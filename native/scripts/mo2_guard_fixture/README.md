# Native installer destination and activation control

On November 24, 2026, a private portable MO2 2.5.3 beta 12 host ran two ordinary `IOrganizer.installMod(archive, name_suggestion)` transactions with MO2's stock Quick Installer. Both suggested a previously absent folder. The first dialog accepted a different new name. The first installed callback observed that new mod disabled and immediately enabled it using the public mod-list API. MO2 persisted the enabled row on shutdown.

The second dialog accepted the name of an existing fixture mod. The stock overwrite dialog offered Merge. MO2 replaced the existing archive member and preserved the separately seeded sibling. In both cases the suggested folder remained absent. The three members of the source archive matched their installed bytes in both actual destinations.

This is a counterexample to a destination or activation guarantee, with a deliberate observer on inert fixture data. The stock host initially created the new mod disabled. The experiment does not measure the frequency of unexpected activation on other installations. Modhunter's `requireProtectedInstall` and host-wide `MODHUNTER_PROTECTED_INSTALLS` refusal still apply before ordinary installation can be dispatched.

### Reproduction

1. Use a fresh, private portable beta-12 host in a disposable Windows account. Install its stock Python loader, Quick Installer, `basic_games` and the repository's `native/scripts/mo2_smoke_plugin/game_modhunter_smoke.py` fixture game. Use the fixture game's private inert executable, Data, Documents and Saves directories. Select the profile `Guard Fixture` with empty downloads, mods and modlist. Set the host's base directory to its own absolute directory and the ordinary mods, profiles, downloads and overwrite directories below it. Keep the normal user instance and profile out of this test.
2. Run `python -B native/scripts/mo2_guard_fixture/fixture.py prepare <fixture>`. Preparation verifies the host and installer SHA-256, game, profile and paths. It creates one inert archive, one existing fixture sentinel and the observer.
3. In that fixture process only, set `MODHUNTER_DISPOSABLE_GUARD_PROBE` to the fixture's absolute directory and launch its own `ModOrganizer.exe --multiple -p "Guard Fixture"`. The observer operates only when the marker, executable directory, active profile, data paths, archive and exact test rows match. It runs both installs, records real callbacks and requests ordinary host shutdown.
4. After shutdown, run `python -B native/scripts/mo2_guard_fixture/fixture.py verify <fixture>`. This rechecks the binaries, observer, archive, six observed events, directory membership, both sets of installed bytes and the persisted profile.

The tested executable SHA-256 was `10bb9f91d565d1a26424ab816b303a014573dd53a7f318a0a9e88cf7c282b45f`. The Quick Installer SHA-256 was `808db649ca9eb63fa8dde4af18193724b2ad1d36bc82c1c58f6f80e406a1d0d1`. Both matched the inspected installed beta-12 binaries. The native result SHA-256 was `fbd257d33bd9d672dddb1c09418153950a100e6a87f59420d73dcf49630cde8e`.

Upstream's proxy passes the name as a suggestion. The installer manager implements interactive rename, merge and replace. The core notifies installer plugins and dispatches mod-installed callbacks after installation. An exact no-replace reservation before extraction and a host-enforced activation veto would have to cover those operations. MO2's backup-mod type forces disabled state but also suppresses regular-mod update handling.
